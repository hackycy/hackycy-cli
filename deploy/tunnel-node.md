# Tunnel Server and Remote Node deployment

This release uses one exact Server, Remote Node and official Client version with FRP 0.70.1. It accepts only a new empty Server state directory (schema v3) and the v5 Client protocol. There is no migration, automatic backup or mixed-version mode. Plan a service interruption while rebuilding accounts, Clients, Tokens and Tunnels.

## Bare metal

1. Stop the old Server and Clients. Keep the entire old Server state directory, including SQLite WAL/SHM files, unchanged. Do not start the new Server against it. If rollback to the old release is needed, use the old binary with that old directory. Previously claimed Remote Nodes can keep running after a Server rollback; migrate Clients away and complete normal removal before relying on that rollback.
2. Install the same exact `ycy` release on the Server and each Remote Node. Give the Server a new empty, private directory, for example `/var/lib/ycy-tunnel-server-v3`. Start `ycy tunnel server --data-dir /var/lib/ycy-tunnel-server-v3` with `YCY_TUNNEL_ADMIN_PASSWORD` set. Keep the Server's Controller identity file together with its schema v3 database; losing the private key cannot be repaired by a new Controller or remote rebind.
3. On each separate Node host, use its own empty, private local filesystem directory. Start `ycy tunnel node --management-bind-address 0.0.0.0 --management-port 7600 --data-dir /var/lib/ycy-tunnel-node`. Retain that directory across process and container restarts. It stores the Node identity, Controller binding, high-water revision and last successful FRPS configuration. Do not share it with another Node or place SQLite WAL/SHM on a cross-host network filesystem.
4. Record the **full** Node fingerprint printed on its first start. Open `http://<server-host>:7500/nodes`, preview `http://<node-public-ip>:7600`, compare the full fingerprints, then confirm claim. The first valid encrypted claim fixes the Controller. A lost Node volume creates a new identity and fingerprint; matching IP:port does not restore the old identity.
5. Configure the Node's local FRPS bind port, HTTP vhost port and public TCP/UDP pool in the Server UI. Set Advertised FRP Address to the public Client-facing host:port and HTTP Ingress Address to the public HTTP host:port. These may differ from the management address and local bind ports under NAT. Wait for a fresh management observation, applied configuration and running FRPS before assigning a Client.
6. Recreate accounts, Clients and Tunnels and connect the new official Client to the Server control endpoint. Verify the Client's assigned Node, applied revision, FRPC login and proxy registration separately. Set HTTP Tunnel DNS to the Node's HTTP ingress host and preserve the Host header. A saved route does not prove DNS or the remote listener works.

The Server control endpoint uses TCP 7500; Local FRPS uses TCP 7000, HTTP 8080 and TCP/UDP 20000-20100 by default. Open Node TCP 7600 from the Server for HTTP/Noise management, TCP 7000 from assigned Clients, and TCP 8080 plus the configured TCP/UDP pool from visitors. If a fixed FRPS or HTTP port is remapped, enter the public mapped port in the Server. Pool ports must map to the same public port numbers. `GET /health` on the Node only proves the management process responds; it does not prove FRPS is running.

Normal Remove first requires no current or pending Clients, then queues a durable disabled snapshot. The Node remains listed as removing until a fresh authenticated status confirms persistent disablement and stopped FRPS. While offline it may still serve old traffic. Force Forget deletes only the Server record; remote FRPS may continue running, old credentials may work, and the Node remains bound to the Controller. Reusing that machine under a new Controller requires stopping the Node and manually clearing its **entire** local state directory, which creates a new identity and fingerprint. There is no product reset or remote rebind command.

## Containers

Use [Server Compose](docker-compose.tunnel.yml) on the Server host and [Node Compose](docker-compose.tunnel-node.yml) on each separate Node host. Set the same exact `YCY_VERSION` release tag on both; the Server also requires `YCY_TUNNEL_ADMIN_PASSWORD`. The Server example uses a **new** `tunnel-server-v3` volume and leaves any old `tunnel-data` volume untouched. Every Node host needs its own persistent `tunnel-node-data` volume. Publish and permit TCP 7600, 7000 and 8080 plus TCP/UDP 20000-20100 at the Node host firewall; configure the same pool in the Server UI. After replacing a container with its volume intact, check that its fingerprint, binding and applied revision remain unchanged before allowing new Client assignments.

Use the same deployment interruption and verification steps as bare metal. Container restart does not mean Node disablement: a claimed Node restores its last successful running configuration unless it has persistently accepted disabled. Management failure or version mismatch leaves remote FRPS state unknown to the Server; it is not proof of shutdown. For this G7 release, the smoke test uses a dedicated Docker network with Server, Node and official Client containers and verifies HTTP, TCP and UDP forwarding after a volume-preserving Node recreation. A production deployment still needs its own firewall and public port checks. The runbook records the tested image tag, FRP build, isolated network and port mapping, observations and expected interruption.
