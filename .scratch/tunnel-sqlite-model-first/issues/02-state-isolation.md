# 决定新旧 Tunnel 状态如何隔离

Type: grilling
Status: resolved
Parent: ../map.md

## Question

在保持用户可指定 `--data-dir` 的前提下，应采用哪些新的固定文件名或内部路径，使 Server 和 Node 不读取旧 SQLite，同时不混用 Server 的 Controller 密钥/会话以及 Node 的初始化标记/FRPS 运行文件？旧文件是否原样留存，版本不匹配或新状态不完整时应如何失败？

## Answer

- `--data-dir` 继续指定用户可选的状态根目录。程序使用固定的内部子目录：Server 为 `<data-dir>/server-state-v1/`，Node 为 `<data-dir>/node-state-v1/`。这里的 `v1` 是新状态布局和新 schema 的起点；未来 schema 演进在该目录内按维护约束处理，不表示兼容旧 `go-v1` 状态。数据库文件可以在各自的新子目录内沿用简短名称；隔离边界是整个子目录，而非只更换 SQLite 文件名。
- Server 的新数据库、Controller 身份密钥、会话密钥、会话记录和会话锁均属于 `server-state-v1/`；Node 的新数据库、初始化标记、FRPS 配置/页面文件及临时传输文件均属于 `node-state-v1/`。两端现有的根目录进程锁继续锁住用户指定的 `--data-dir`；除该锁外，业务状态只读写各自的新子目录，不读取、删除或清理旧状态文件。
- 没有已正式上线的旧 Node，因此不设计旧 Node 数据检测、FRPS 进程接管或自动清理流程。旧状态兼容和切换均不属于本次设计。
- 新子目录不存在或为空时可首次初始化。若新状态已开始初始化或已投入使用，但必需的数据库、身份密钥、会话密钥或初始化标记缺失、损坏，或 schema 结构不匹配，则启动报错；本次不自动升级、生成替代身份或重建空数据库。未来需要升级已部署数据库时，另按维护约束设计 migration 生命周期。明确重置时由操作者移走整个新子目录，再以空状态初始化。运行中可再生成的 FRPS 配置文件不等同于身份或数据库缺失，具体恢复规则留给“决定 Node 身份与运行状态的模型”。
